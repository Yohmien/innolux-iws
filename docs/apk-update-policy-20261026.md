# APK 更新策略调整

## 范围与决定

本次在现有 APK 管理和 PDA 更新门禁上增加版本级强制更新开关，并改善初始化和上传错误提示。允许修改代码、文档和升级脚本；不执行真实数据库写入、发布或部署。

- APK 版本新增 `forceUpdate` 布尔值，默认开启。上传表单可设置，管理员也可修改已有版本；关闭后 PDA 不因版本不同阻止登录。
- 管理接口上传 multipart 增加可选 `forceUpdate`，默认 `true`；`POST /system/apk/{releaseId}/force-update?forceUpdate=true|false` 修改策略，复用 `system:apk:publish` 权限。重复上传仍复用原记录，不借重复上传修改原策略。
- 版本视图统一返回 `forceUpdate`。`GET /app/apk/latest` 在不存在对应已发布版本时返回成功且 `data:null`，PDA 自动跳过此次更新检查。非法查询、同名歧义、网络失败和服务错误不作为无版本处理。历史和下载接口保持原语义。
- 强制更新门禁中可编辑当前服务器地址和端口，复用现有配置存储与校验。保存后取消旧检查和下载，清理旧服务器的版本与下载状态，使用新地址重新检查；旧异步回调不得覆盖新状态。
- APK 上传存储失败返回中文可操作提示；命中 MinIO API 端口错误时明确说明 API 端口及代理配置，服务端保留原始堆栈。

用户已确认：空版本是服务端没有该包的已发布版本；服务设置需要同时支持服务器地址和端口。版本级开关、默认开启和沿用发布权限为本次实现选择。

## 验收

1. 上传表单和版本历史正确展示、提交与修改开关，失败后保留服务器真实值；无权限不显示修改入口。
2. 最新已发布版本携带开关；无发布版本成功返回空；未发布版本不泄漏。
3. PDA 同版本、非强制版本、无发布版本均允许原登录流程；强制新版保持门禁；实际请求错误仍提示并可设置服务。
4. 门禁中的服务配置校验与现有设置一致，保存后重查，旧请求及下载/安装回调不会污染新服务器状态。
5. 存储端口错误与其他存储写入错误均有明确提示，失败不新增版本记录。
6. 数据库新增列与实体映射一致，初始化和升级脚本覆盖新列；真实库不执行脚本。静态、单元、浏览器隔离验证与 Android 真机验收分别记录。

## 数据库证据与上线

2026-10-26 按当前 `dev` 配置定位到 `localhost:3306/innolux-iws`，MCP `SHOW GRANTS` 核实账号只有 SELECT/SHOW 权限。`db_describe` 和 `information_schema.TABLES` 均确认本机目标不存在 `sys_apk_release`，存在 `sys_oss`；不能据此推断日志所在部署库。MCP 对 `VERSION()` 查询拒绝，数据库具体版本未从该查询取得。

交付字段为 `force_update`，非空、默认开启。已有库先按实际库核验并执行升级脚本，再部署后端与 Web，最后部署 PDA。未迁移不得启动依赖新列的后端。首次初始化使用同步更新的初始化入口。

已在独立 MySQL 8.0.45、`127.0.0.1:35241` 和专用数据目录执行验证：首次补列将旧记录置为 `1`，重跑保留显式 `0`，Boolean 省略值与显式 `0` 往返正确；nullable、默认 `0`、缺表、错误 database、错误 schema 五个场景均被门禁拒绝且未改写结构。共 8 个数据库用例和 3 项静态检查通过，验证服务已停止。真实部署库未执行脚本，`innolux-iws` 本机目标实际仍缺 APK 表。
