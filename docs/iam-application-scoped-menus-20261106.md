# IWS 应用维度角色菜单权限

## 目标

`iws-a`、`iws-b` 拥有各自的菜单定义，并允许同一角色在两个应用中选择不同
菜单。现有全局 `sys_role_menu` 授权继续作为兼容基线：某个角色没有配置应用
独立授权时沿用原全局菜单；一旦配置了应用独立授权，该应用只使用自己的菜单
集合，空集合也表示该应用没有菜单。

## 数据模型

- 为 `sys_menu` 增加 `application_id`。`iws-a`、`iws-b` 保存应用标识，
  `*` 只表示认证中心、AI、共享监控/工具和官网等公共菜单。空白归属默认写为
  `iws-a`；每个 IWS 的业务菜单必须使用自己的应用标识。菜单名称、路由、组件、
  权限串和父子关系均在该应用范围内维护。
- 保留 `sys_role_menu`，不修改其主键和现有消费者。
- 新增 `sys_role_menu_scope(role_id, application_id)`，记录角色已显式配置某
  个应用，即使该应用最终没有菜单。
- 新增 `sys_role_menu_application(role_id, application_id, menu_id)`，保存
  角色在指定应用下的菜单和按钮权限。
- 两个新表均以 `(role_id, application_id)` 和
  `(role_id, application_id, menu_id)` 为业务主键。

## 生效规则

1. 菜单管理页先选择 IWS 应用，再展示该应用的 `application_id=<当前应用>`
   和 `application_id=*` 的完整目录、菜单、按钮树。
2. 应用为 `iws-a` 或 `iws-b` 时，逐角色执行以下规则：
   - 存在该角色与应用对应的 `sys_role_menu_scope` 时，只取
     `sys_role_menu_application` 中的菜单，并再次限制菜单属于当前应用或 `*`。
   - 不存在 scope 时，继续取 `sys_role_menu` 中的全局菜单。
3. 一个用户拥有多个角色时，合并每个角色按上述规则得到的结果。
4. 认证中心自身和未声明 `iam.client.application-id` 的进程继续使用全局菜单。
5. 认证中心的接入资格计算必须合并全局和全部应用独立权限，确保门户可以同时
   判断 `iam:app:iws:a`、`iam:app:iws:b` 等应用入口。
6. 超级管理员在 IWS 应用内也只读取该应用和共享菜单；在认证中心管理端可以
   配置全部应用。

## 管理界面

- “菜单管理”增加“应用范围”选择；新增、修改、删除和查询都作用于选中应用
  或共享菜单。
- “角色管理 → 分配权限 → 菜单权限”增加“应用范围”选择，并显示选中应用的
  完整菜单定义。
- 选项只来自认证中心已启用且 `enabled=true` 的 `type=IWS` 应用，并始终保留
  独立的“共享菜单”选项；前端不写死 `iws-a`、`iws-b`。
- `iws-b` 未配置或 `IAM_IWS_B_ENABLED=false` 时，菜单管理和角色权限页均不
  展示 IWS-B，后端也拒绝把菜单定义或角色授权写入 `iws-b`。
- 切换应用时保留尚未提交的各应用勾选状态，提交时只写入发生变化的独立应用
  授权，未修改的应用继续沿用原配置。
- 首次未配置时显示全局菜单作为继承值；保存后创建应用独立授权。
- 数据权限仍属于角色的全局配置，不随 IWS 应用拆分。

## 接口

- `GET /system/menu/list?applicationId=...`
  - 查询选中应用的完整菜单定义。
- `GET /system/menu/applicationScopes`
  - 返回已启用的 IWS 应用。
- `GET /system/menu/roleMenuTreeselect/{roleId}?applicationId=...`
  - 返回菜单目录、当前生效的勾选键。
  - 新增 `configured`，区分“继承全局菜单”和“已配置但菜单为空”。
- `PUT /system/role/permission`
  - 保持原 `menuIds`、`deptIds` 兼容。
  - 新增 `applicationMenuIds: Map<String, Long[]>`。
  - 只为请求中出现的应用重建 scope 和菜单集合。

## 兼容与失败边界

- 数据库升级新增菜单应用列和两张角色作用域表，不复制或删除现有
  `sys_role_menu` 数据。存量菜单默认回填为 `iws-a`，仅公共菜单根树
  `系统管理`、`系统监控`、`系统工具`、`AI会话` 和 `INNOLUX官网` 回填为 `*`。
  重复执行不会覆盖已有的 `iws-b` 业务菜单。
- 升级前发布的后端继续读取全局菜单；升级后的后端在没有应用独立配置时结果不变。
- 应用 ID 必须来自认证中心已登记且启用的应用；非法或未知 ID 拒绝保存。
- 角色删除和菜单删除需要同步清理应用独立关联。

## 验收

- 同一角色配置 `iws-a` 菜单集合 A、`iws-b` 菜单集合 B，两个后端返回不同菜单树。
- 菜单管理页切换 A/B 后分别显示两个应用自己的完整菜单定义。
- 停用 IWS-B 后，菜单管理和角色权限页均不再出现 IWS-B，且共享菜单不受影响。
- 角色存在应用 scope 且菜单为空时，该应用返回空菜单，不回退全局菜单。
- 未配置应用 scope 的角色继续返回原全局菜单。
- 多个角色分别继承全局和覆盖应用时，用户结果按角色正确合并。
- 角色权限页切换 A/B 后分别保存，互不覆盖。
- 角色删除、菜单级联删除后，新关联表无孤儿数据。
- 现有认证中心登录、门户应用授权、角色数据权限和菜单测试保持通过。
- 空库初始化直接在 `sys_menu` 建表中包含 `application_id` 和应用索引，种子
  菜单默认写入 `iws-a`，公共菜单显式调整为 `*`；最终验收同时检查两张角色
  应用菜单表。

## 空库实测

已使用本机 MySQL 8.0.45 启动临时无密码实例执行完整
`iws_init_from_empty.ps1`，结果为：

- 表总数 `183`，WMS 表 `77`，系统菜单 `255`。
- `sys_menu.application_id` 默认值为 `iws-a`，`idx_sys_menu_application`
  检查通过。
- 255 条菜单中 `100` 条为共享菜单、`155` 条为 IWS-A 业务菜单，无其他范围。
- `sys_role_menu_scope`、`sys_role_menu_application` 均存在。
- 非空库再次执行被入口脚本拒绝，不会覆盖已有 schema。
- 升级脚本在隔离库连续执行成功；公共菜单保持 `*`、业务菜单回填 `iws-a`，
  已存在的 `iws-b` 测试菜单保持不变。
